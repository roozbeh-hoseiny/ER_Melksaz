# Architecture Rules Summary

Version: 1.0

---

# Purpose

This document is the condensed version of the architecture handbook.

It serves as the mandatory checklist that both engineers and AI agents should mentally execute before implementing any feature.

If a detailed rule conflicts with this summary, the detailed rule takes precedence.

---

# Rule 1 — Business Comes First

Business requirements always have higher priority than technical preferences.

Technology exists to serve the business.

---

# Rule 2 — The Domain Owns Behaviour

Only the Domain may contain:

* Business rules
* Business decisions
* Business calculations
* Business invariants

Business logic must never appear elsewhere.

---

# Rule 3 — The Application Coordinates

The Application Layer:

* Loads Aggregates.
* Invokes Domain behaviour.
* Coordinates transactions.
* Persists changes.
* Publishes events.

It never implements business rules.

---

# Rule 4 — Infrastructure Implements

Infrastructure provides technical implementations.

Examples:

* Database
* Messaging
* Cache
* Email
* Authentication
* Logging

Infrastructure never owns business behaviour.

---

# Rule 5 — API Transports

The API:

* Receives requests.
* Invokes the Application.
* Returns responses.

Nothing more.

---

# Rule 6 — Dependencies Point Inward

Allowed:

```text id="p1m9vs"
API
↓

Application
↓

Domain

Infrastructure
↓

Application
↓

Domain
```

Forbidden:

* Domain → Infrastructure
* Domain → API
* Application → Infrastructure Implementation

---

# Rule 7 — Modules Own Their Business

Every business concept belongs to exactly one module.

No module may directly access another module's internal implementation.

---

# Rule 8 — Aggregates Protect Consistency

Aggregate Roots:

* Own transactions.
* Protect invariants.
* Control child Entities.

Repositories expose Aggregate Roots only.

---

# Rule 9 — Value Objects Are Immutable

Value Objects:

* Have no identity.
* Are immutable.
* Are compared by value.
* Encapsulate behaviour.

---

# Rule 10 — Commands Change State

Commands:

* Modify business state.
* Produce side effects.
* Execute business behaviour.

Commands do not retrieve read models.

---

# Rule 11 — Queries Read Data

Queries:

* Retrieve information.
* Have no side effects.
* Never modify business state.

---

# Rule 12 — Vertical Slice Per Use Case

One business use case equals one Vertical Slice.

Each slice owns:

* Command/Query
* Handler
* Validator
* Endpoint
* Tests

---

# Rule 13 — Explicit Boundaries

Always make explicit:

* Module boundaries.
* Aggregate boundaries.
* Layer boundaries.
* Transaction boundaries.
* Public contracts.

Avoid hidden architecture.

---

# Rule 14 — Framework Independence

The Domain must never depend on:

* ASP.NET Core
* EF Core
* Redis
* RabbitMQ
* MassTransit
* SQL
* Logging
* Configuration

Technology is replaceable.

---

# Rule 15 — Shared Kernel Must Stay Small

Only place stable, framework-independent abstractions in the Shared Kernel.

Never move business concepts there merely to reduce duplication.

---

# Rule 16 — AI Must Reuse Existing Patterns

Before generating new abstractions, the AI must:

* Search for existing patterns.
* Follow existing conventions.
* Extend rather than replace.

Consistency is mandatory.

---

# Rule 17 — Every Feature Includes Tests

Every generated feature should include:

* Unit Tests
* Integration Tests
* Test Builders (where applicable)

Production code without tests is incomplete.

---

# Rule 18 — Architecture Is Never Broken

The AI must never intentionally violate:

* Clean Architecture
* DDD
* CQRS
* Module Boundaries
* Dependency Rule

If a request conflicts with these rules, the AI should highlight the conflict.

---

# Rule 19 — Documentation Evolves with Code

Significant architectural changes require updates to:

* ADRs
* Architecture Handbook
* AI Handbook

Documentation is part of the implementation.

---

# Rule 20 — Consistency Over Creativity

When several technically valid solutions exist, always choose the one that is most consistent with the existing repository.

The goal is not to produce the most novel code.

The goal is to produce code that appears to have been written by the same engineering team.

---

# AI Pre-Implementation Checklist

Before writing any code, verify:

* Business module identified.
* Correct layer identified.
* Existing patterns reviewed.
* Architecture preserved.
* Dependencies valid.
* Naming consistent.
* Tests planned.
* No architectural violations introduced.

---

# Final Principle

The architecture handbook is the source of truth.

Every implementation—whether written by a human or generated by AI—must preserve the architecture, strengthen consistency, and protect the long-term maintainability of the repository.
