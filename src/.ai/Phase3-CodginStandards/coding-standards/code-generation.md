# Code Generation

Version: 1.0

---

# Purpose

This document defines the mandatory standards for AI-assisted and automated code generation throughout the repository.

Generated code must be indistinguishable from manually written code in terms of quality, readability, correctness, and maintainability.

Every generated artifact must comply with the repository's architecture, coding standards, and design principles.

---

# Primary Principle

Generate production-quality code.

Generated code is not a prototype.

It is expected to be maintainable, testable, and suitable for long-term evolution.

---

# Repository Standards

Every generated artifact must follow all repository standards, including:

* Architecture
* Naming
* Folder structure
* Coding style
* Dependency Injection
* Exception handling
* Validation
* Logging
* Testing
* Documentation

Generated code is never exempt from repository rules.

---

# Prefer Existing Patterns

Before introducing a new abstraction, pattern, or convention:

* Search the repository.
* Reuse existing implementations.
* Follow established naming.
* Match existing architectural decisions.

Consistency is preferred over novelty.

---

# Preserve Architecture

Generated code must respect:

* Clean Architecture
* Dependency Rule
* DDD boundaries
* CQRS (where applicable)
* Module ownership
* Layer responsibilities

Never introduce architectural shortcuts.

---

# Small, Focused Types

Generated classes should have one clear responsibility.

Avoid generating "God Classes" or large utility classes.

---

# Explicit Code

Prefer explicit implementations over hidden behaviour.

Generated code should be easy to:

* Read
* Debug
* Review
* Refactor

Avoid unnecessary magic.

---

# Dependencies

Use constructor injection.

Never generate:

* Service Locator
* Static dependency access
* Hidden runtime resolution

Dependencies must remain explicit.

---

# Error Handling

Generated code should:

* Validate inputs.
* Preserve stack traces.
* Handle exceptions appropriately.
* Avoid swallowing exceptions.

Business failures should follow repository Result conventions.

---

# Logging

Generate logging only when it adds operational value.

Logging should:

* Be structured.
* Use appropriate log levels.
* Never expose sensitive information.

Do not generate excessive logging.

---

# Validation

Generated code should:

* Validate external input.
* Protect Domain invariants.
* Avoid duplicate validation.
* Follow repository validation conventions.

---

# Mapping

Mappings should be:

* Explicit
* Predictable
* Free of business logic

Avoid reflection-based mapping.

---

# Performance

Generated code should:

* Avoid obvious inefficiencies.
* Prevent unnecessary allocations.
* Use asynchronous APIs correctly.
* Avoid premature optimisation.

Readability remains the priority unless profiling demonstrates otherwise.

---

# Testing

When generating new behaviour, also generate appropriate tests where repository conventions require them.

Tests should:

* Verify observable behaviour.
* Be deterministic.
* Follow Arrange–Act–Assert.
* Use meaningful names.

---

# Documentation

Generate documentation when:

* A public API is introduced.
* A complex algorithm requires explanation.
* A significant architectural decision is implemented.

Do not generate redundant comments.

---

# Generated Files

Generated source files should clearly indicate whether they are intended to be regenerated.

Example header:

```text id="t3w9mp"
// <auto-generated>
// This file was generated by ProtoWeaver.
// Manual changes may be overwritten.
// </auto-generated>
```

Files intended for manual editing should not contain this header.

---

# Partial Classes

When generated types require user customization, prefer partial classes.

Separate:

* Generated code
* Manual code

Never overwrite manually maintained files.

---

# Deterministic Generation

Given the same inputs, the generator should produce the same output.

Avoid non-deterministic ordering, random identifiers, or unstable formatting.

Deterministic generation improves code review and version control.

---

# Formatting

Generated code must follow repository formatting conventions.

Avoid producing code that requires manual formatting before commit.

---

# Naming

Generated identifiers should:

* Use the Ubiquitous Language.
* Follow repository naming conventions.
* Avoid abbreviations unless already established.
* Be intention revealing.

---

# Backward Compatibility

When generating code for existing systems:

* Preserve public contracts where possible.
* Avoid unnecessary breaking changes.
* Generate migration-friendly code.

---

# AI Responsibilities

When generating code, the AI must:

* Follow every repository standard.
* Reuse existing architectural patterns.
* Generate readable and maintainable code.
* Avoid unnecessary abstractions.
* Preserve architectural boundaries.
* Produce deterministic output.

---

# Anti-Patterns

Avoid generating:

* Service Locator patterns.
* Hidden dependencies.
* Reflection-heavy implementations.
* Business logic inside mappers.
* Duplicate code.
* Dead code.
* Unused abstractions.
* Placeholder implementations marked for future completion without explicit instruction.

---

# Code Generation Checklist

Before completing generated code, verify:

* Repository standards are followed.
* Architecture is respected.
* Naming is consistent.
* Dependencies are explicit.
* Validation is correct.
* Logging is appropriate.
* Tests are provided when required.
* Documentation is updated where necessary.
* Generated output is deterministic.

---

# Guiding Principle

Generated code should require no special treatment.

If a reviewer cannot distinguish between generated code and expertly written manual code, the generator has succeeded.
